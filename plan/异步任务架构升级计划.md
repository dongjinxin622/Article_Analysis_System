## 一、现状对比分析

### 1.1 架构对比

| 维度 | 现有项目（SciPDF） | case_one 项目（Day37） | 差距评估 |
|------|-------------------|----------------------|---------|
| **任务引擎** | Celery + Beat | 自研 Redis Stream 引擎 | ⚠️ Celery 功能强大但复杂，Redis Stream 更轻量灵活 |
| **任务状态存储** | Redis（临时，2小时）+ PostgreSQL（元数据） | PostgreSQL（持久化）+ Redis Stream（消息队列） | 🔴 现有项目任务状态易丢失 |
| **进度推送** | WebSocket | SSE（Server-Sent Events） | ⚠️ WebSocket 双向通信过重，SSE 单向推送更轻量 |
| **任务取消** | ✅ 支持（Celery revoke） | ✅ 支持（数据库状态标记） | ✅ 相当 |
| **任务重试** | ✅ 支持（Celery 内置） | ✅ 支持（指数退避，最多 N 次） | ✅ 相当 |
| **死信机制** | ❌ 不支持 | ✅ TaskDeadLetter 表 | 🔴 现有项目无法追踪超过重试上限的任务 |
| **心跳机制** | ❌ 不支持 | ✅ 每 30 秒心跳刷新 | 🔴 现有项目无法检测卡死的任务 |
| **孤儿任务恢复** | ❌ 不支持 | ✅ OrphanScavenger 定期扫描 | 🔴 现有项目进程重启后任务丢失 |
| **任务管理 UI** | ❌ 不支持 | ✅ Tasks.vue 完整界面 | 🔴 现有项目缺乏任务监控界面 |
| **水平扩展** | ✅ 支持（Celery Worker） | ✅ 支持（多 Worker 进程） | ✅ 相当 |
| **任务指标统计** | ❌ 不支持 | ✅ 时序统计（完成率、失败率） | ⚠️ 现有项目缺乏任务监控指标 |

### 1.2 核心问题诊断

#### 🔴 严重问题（必须解决）

1. **任务状态易丢失**
   - 现有项目：任务状态存储在 Redis，2小时后过期
   - 问题：进程重启或 Redis 重启后，任务状态无法恢复
   - 影响：用户无法查看历史任务，长时间运行的任务可能丢失

2. **缺乏死信机制**
   - 现有项目：任务失败后直接标记为 failed
   - 问题：超过重试上限的任务无法追踪和诊断
   - 影响：无法分析任务失败的根本原因

3. **缺乏心跳和孤儿任务恢复**
   - 现有项目：任务执行过程中无法检测卡死
   - 问题：进程崩溃后，任务永远停留在 running 状态
   - 影响：任务永远不会完成，用户体验差

4. **缺乏任务管理界面**
   - 现有项目：只能通过 API 查询任务状态
   - 问题：用户无法直观查看任务列表、进度、失败原因
   - 影响：运维困难，用户体验差

#### ⚠️ 中等问题（建议解决）

1. **WebSocket 过重**
   - 现有项目：使用 WebSocket 推送进度
   - 问题：WebSocket 是双向通信，对于单向进度推送过重
   - 建议：改用 SSE（Server-Sent Events）更轻量

2. **缺乏任务指标统计**
   - 现有项目：无法查看任务完成率、失败率等指标
   - 问题：无法监控系统健康状况
   - 建议：增加任务指标统计和图表展示

3. **任务超时控制不精细**
   - 现有项目：Celery 任务超时配置较简单
   - 问题：无法为不同类型的任务设置不同的超时时间
   - 建议：引入细粒度的超时控制

## 二、升级方案

### 2.1 方案选择

#### 方案 A：保持 Celery，增强功能（推荐 ⭐⭐⭐）

**核心思路**：保留 Celery 作为任务引擎，补充死信、心跳、任务管理等缺失功能。

**优点**：
- ✅ 不破坏现有架构，改动最小
- ✅ Celery 生态成熟，文档丰富
- ✅ 已有 Celery 基础设施（Redis Broker、Beat 调度器）
- ✅ 团队熟悉 Celery，学习成本低

**缺点**：
- ⚠️ Celery 的 Redis Broker 不支持消息确认（XACK）
- ⚠️ 需要额外实现任务状态持久化
- ⚠️ 无法完全复制 case_one 的 Redis Stream 架构

**改动范围**：
- 新增死信表（task_dead_letter）
- 新增心跳机制（TaskItem 表增加 running_at 字段）
- 新增任务管理 UI
- 改用 SSE 替代 WebSocket（可选）
- 新增任务指标统计

**预估工作量**：5-7 天

#### 方案 B：迁移到 Redis Stream（不推荐 ⭐⭐）

**核心思路**：完全复制 case_one 的 Redis Stream 架构，替换 Celery。

**优点**：
- ✅ 架构统一，代码风格一致
- ✅ Redis Stream 功能强大，支持消息确认
- ✅ 可以完全复用 case_one 的代码

**缺点**：
- ❌ 破坏性变更，需要重写所有 Celery 任务
- ❌ 团队需要学习新的任务引擎
- ❌ 失去 Celery 生态（Beat 调度器、Flower 监控等）
- ❌ 工作量大，风险高

**改动范围**：
- 引入 AsyncTaskEngine、TaskWorker、OrphanScavenger
- 重写所有 Celery 任务（pdf_tasks、ner_tasks、re_tasks 等）
- 新增任务数据模型（TaskJob/TaskItem/TaskDeadLetter）
- 新增任务服务层
- 新增任务管理 UI
- 删除 Celery 相关代码

**预估工作量**：15-20 天

#### 方案 C：混合架构（折中方案 ⭐⭐⭐⭐）

**核心思路**：保留 Celery 处理简单任务，引入 Redis Stream 处理复杂批量任务。

**优点**：
- ✅ 渐进式升级，风险可控
- ✅ 两种引擎互补，发挥各自优势
- ✅ Celery 处理单文件 PDF 解析、NER 等简单任务
- ✅ Redis Stream 处理批量清洗、综合分析等复杂任务

**缺点**：
- ⚠️ 需要维护两套任务引擎
- ⚠️ 架构复杂度增加

**改动范围**：
- 引入 Redis Stream 引擎（用于批量任务）
- 保留 Celery（用于简单任务）
- 新增任务管理 UI
- 新增死信和心跳机制（仅针对 Redis Stream 任务）

**预估工作量**：10-12 天

### 2.2 推荐方案：方案 A（保持 Celery，增强功能）

**理由**：
1. **改动最小**：不需要重写现有任务，只需补充缺失功能
2. **风险最低**：保留 Celery 基础设施，不破坏现有架构
3. **工作量可控**：5-7 天即可完成核心功能
4. **团队友好**：无需学习新技术栈

```python
class OrphanScavenger:
    """孤儿任务清道夫 - 定期扫描超时/卡死的任务"""
    
    def __init__(self, stale_timeout: int = 600):
        self.stale_timeout = stale_timeout  # 10 分钟无心跳视为卡死
    
    async def scan_once(self):
        """单次扫描"""
        # 1. 查询所有 heartbeat_at < now() - stale_timeout 的任务
        # 2. 如果 retry_count < max_retries，重新入队
        # 3. 否则标记为 failed，记录死信
    
    async def start(self):
        """启动扫描循环"""
        
    async def stop(self):
        """停止扫描"""
```
